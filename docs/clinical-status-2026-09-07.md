## 二、`graphs.json` 与 `clinical-a/b.json` 的预算口径

**结算用的是 `clinical-a.json` / `clinical-b.json` 的 `budget`。** `src/game/catalog.ts` 用 `{...c}` 展开这两份 JSON 的整条记录，只用 `graphs.json` 的 `presentation` 覆盖主诉、病史与体征，从不覆盖 `budget`；超支判定（`director.ts`、`costs.ts`）读的是展开后的那个值。

**`graphs.json` 顶层的 `budget` 是设计文档基线。** 它由 `parser.ts` 从「预算」或「DIP 病组与预算」栏解析出来，不参与结算。

两者必须写同一个数。`src/content/clinical/clinical.test.ts` 新增了一条测试逐例比对，任何一侧改了另一侧没跟上就会失败。C006 的 ¥1,800 与「急诊留观·低血糖昏迷」已经对齐（F03）。

`dipGroup` 的措辞仍有 13 例与设计文档不同（F04），金额一致，只是描述性文字改写，例如 C003 写成「住院·急性下壁心肌梗死，经皮冠状动脉介入」而设计文档写「住院·急性心肌梗死，经皮冠状动脉支架植入」。改哪一边属于病组命名判断，列在下面的待主人核。

## 三、底牌能不能被处置到

原记录 A3-04 说的是：交班里明确写了「今晚再查」却没写查什么、什么时候，玩家做完通用的床旁复核后，只能留下一个「下一次评估时间」，无法确认自己解决了病例的核心问题。

现在，138 条带底牌的预设在决策幕都多出一项处置：

- 底牌属于交接或既往复查缺项的，选项是「逐项追问交接与既往记录里没有写明的用药和检查」，回报写出要补做的项目、复查时点和复核的人。
- 底牌属于患者本人隐瞒的，选项是「单独向患者本人追问尚未说明的经过」，回报写出记进病历的经过和接下来要核对的项目。

选项文本只说医生做什么，不提前说出底牌是什么。这一项**不花行动点、不产生费用**，花的是本班的分钟数和体力；同一幕里的「按病情安排处置」和「请专科共同评估」都要花行动点和费用。三条正确路线因此付的是不同的东西。

出院口径（A3-05）方面，每条预设现在公布自己的风险关闭条件 `riskClosure`：需要哪些 flag 才算这条预设自己的风险已经关闭，以及每一条缺失时该显示的句子（「尚未逐项核对交接与既往记录里没有写明的用药和检查，也没有写明要补做哪些复查、在什么时点由谁复核。」这样的完整句）。引擎侧还没有消费这个字段，见跨文件需求。
